Telegram bots are one of the most reliable interfaces for real-time DevOps alerts, cryptocurrency trading triggers, and remote system administration. However, naive implementations crash on unhandled network drops or trigger rate-limit blocks when broadcasting sudden incident surges.

Here is how to engineer resilient automation bots in Go and Node.js.

---

## 1. Architecture: Webhooks vs Long-Polling

```text
Pattern A: Long-Polling (Ideal for Local Daemons & Firewalled Servers)
┌──────────────┐                  ┌────────────────┐
│  Local Bot   │ ─── GetUpdates ─►│  Telegram API  │ (Holds connection 30s)
└──────────────┘ ◄── Updates ──── └────────────────┘

Pattern B: Webhook Pipeline (Ideal for Cloud Edge Services)
┌──────────────┐                  ┌────────────────┐
│ Telegram API │ ─── HTTPS POST ─►│ Reverse Proxy  │ ──► [Bot Handler]
└──────────────┘                  │ (TLS / NGINX)  │
                                  └────────────────┘
```

- **Use Long-Polling** when deploying internal infrastructure monitors behind NAT firewalls where opening inbound ports is prohibited.
- **Use Webhooks with Secret Tokens** (`X-Telegram-Bot-Api-Secret-Token`) for public cloud deployments to eliminate polling overhead.

## 2. Outbound Message Queueing & Rate Limiting

Telegram restricts bots to sending no more than **30 messages per second** globally, and **1 message per second per chat**. Without client-side token bucket rate limiting, bulk alert broadcasts result in HTTP 429 penalties:

```go
package bot

import (
	"context"
	"time"
)

type AlertDispatcher struct {
	rateLimiter *time.Ticker
	queue       chan Message
}

type Message struct {
	ChatID int64
	Text   string
}

func NewAlertDispatcher(bufferSize int, interval time.Duration) *AlertDispatcher {
	return &AlertDispatcher{
		rateLimiter: time.NewTicker(interval), // e.g. 50ms interval (~20 msgs/sec max)
		queue:       make(chan Message, bufferSize),
	}
}

func (d *AlertDispatcher) Start(ctx context.Context, sendFn func(m Message) error) {
	for {
		select {
		case <-ctx.Done():
			return
		case msg := <-d.queue:
			<-d.rateLimiter.C
			if err := sendFn(msg); err != nil {
				// Backoff and re-enqueue if rate limited
				time.Sleep(1 * time.Second)
				d.queue <- msg
			}
		}
	}
}
```

## 3. Production Daemonization via Systemd

Avoid running automation scripts inside transient `tmux` or `screen` sessions. Use standard `systemd` unit files for automated restarts on failure and crash logging:

```ini
# /etc/systemd/system/telegram-bot.service
[Unit]
Description=Telegram Infrastructure Alert Bot
After=network.target

[Service]
Type=simple
User=ops
WorkingDirectory=/opt/telegram-bot
ExecStart=/opt/telegram-bot/bin/bot-daemon
Restart=always
RestartSec=5s

# Hardening
NoNewPrivileges=true
ProtectSystem=full
EnvironmentFile=/etc/telegram-bot/secrets.env

[Install]
WantedBy=multi-user.target
```

```bash
# Reload systemd and enable automatic boot startup
sudo systemctl daemon-reload
sudo systemctl enable --now telegram-bot.service
sudo journalctl -u telegram-bot.service -f
```

Combining rate-limited outbound dispatch with systemd process supervision ensures your automation bots stay online indefinitely.
