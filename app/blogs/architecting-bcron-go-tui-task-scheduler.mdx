`cron` is one of those Unix tools everyone respects and nobody enjoys using.

You open `crontab -e`, write a schedule you double-checked on crontab.guru, and hope the environment matches your shell. A week later you find out a backup script has been failing the whole time, because the output went to local mail that nobody reads.

The heavy alternatives (Rundeck, Airflow, Temporal) are built for teams and pipelines. I just wanted to schedule a handful of scripts on my Mac or a server and see what happened when they ran. So I built [bcron](https://github.com/pawiromitchel/bcron) in Go: one binary with a daemon, a CLI and a terminal UI.

To be upfront about scope: bcron runs tasks at a time you choose. It doesn't do recurring cron-style schedules.

## What it looks like

![bcron's terminal UI with a task list and task details](/images/projects/bcron.png)

Tasks on the left, details for the selected one on the right: command, scheduled time, status and when it ran. The keys are what you'd guess:

| Key | Action |
| :--- | :--- |
| `n` / `e` / `d` | New, edit, delete a task |
| `enter` | Task details |
| `h` | Run history with the full stdout and stderr |
| `f` | Cycle the status filter |
| `r` | Refresh |
| `q` | Quit (the daemon keeps running) |

The same things work from the command line:

```bash
bcron add "./backup.sh" --at "2026-02-05 02:00 UTC" --name "backup"
bcron list
bcron run 1       # run it right now
bcron logs 1      # output from the last run
bcron history 1   # every run
```

`--at` accepts ISO 8601, a time with a zone abbreviation (`14:30 EST`), or a separate `--timezone "America/New_York"` flag.

## How it's put together

There are two parts: a daemon that runs tasks, and the CLI/TUI you interact with. They don't talk to each other directly. Both read and write the same SQLite database at `~/.config/bcron/bcron.db`.

```text
┌──────────────┐        ┌──────────────────────┐
│  bcron TUI   │        │     bcron daemon     │
│  bcron CLI   │        │  checks every 30s,   │
└──────┬───────┘        │  max 10 running      │
       │                └──────────┬───────────┘
       │   read / write            │   read / write
       ▼                           ▼
┌──────────────────────────────────────────────┐
│        SQLite  ~/.config/bcron/bcron.db      │
│        tasks, executions, stdout/stderr      │
└──────────────────────────────────────────────┘
```

The upside is that a whole class of problems goes away. There's no socket or protocol to maintain, the UI opens instantly because it's just a query, and if the daemon is down you can still see and edit your tasks.

### Starting the daemon

`bcron daemon start` re-runs its own binary with a `--daemon-mode` flag, doesn't wait for it, and records the PID in `~/.config/bcron/bcron.pid`:

```go
startCmd := exec.Command(binaryPath, "--daemon-mode", "--daemon-pid-file", pidFile)
startCmd.Stdout = nil
startCmd.Stderr = nil
startCmd.Stdin = nil

if err := startCmd.Start(); err != nil {
	return fmt.Errorf("failed to start daemon: %w", err)
}

// Don't wait for the process (let it run in background)
go startCmd.Wait()
```

You mostly don't have to think about it. Adding a task when the daemon isn't running starts it for you.

### Checking for work

The daemon wakes up every 30 seconds and asks SQLite for anything that's due:

```sql
SELECT id, name, command, scheduled_time, timezone, status, created_at, updated_at
FROM tasks
WHERE status = ?
AND datetime(scheduled_time) <= datetime('now')
ORDER BY scheduled_time ASC
```

Each due task runs in its own goroutine, with a limit of 10 at a time. When that limit is reached, the remaining tasks stay `pending` and get picked up on the next check:

```go
if currentRunning >= s.maxConcurrent {
	log.Printf("Max concurrent tasks (%d) reached, skipping task %d", s.maxConcurrent, task.ID)
	continue
}
```

That's simpler than a proper queue, and for a few scripts a day, a 30-second delay doesn't matter. The trade-off is that nothing runs at an exact second. Anything scheduled can start up to 30 seconds late.

Commands run through `sh -c`. Scripts get their interpreter from the shebang or the file extension (`.sh`, `.py`, `.rb`, `.pl`, `.js`, `.php`), and every run has a one-hour timeout.

### Notifications

One feature I use constantly: desktop notifications. On macOS, bcron sends a notification when a task starts, succeeds or fails, using `osascript`, so there's nothing extra to install:

```go
script := fmt.Sprintf(`display notification "%s" with title "%s"`, message, title)
cmd := exec.Command("osascript", "-e", script)
```

On Linux it skips notifications quietly instead of erroring.

## An MCP server, too

bcron also ships a small [MCP](https://modelcontextprotocol.io) server (in `mcp/`), so an AI assistant like Claude can schedule tasks, list and cancel them, read their logs, and start the daemon. Whatever it schedules shows up in the TUI like any other task.

## Limitations

- Tasks are one-off. There are no recurring schedules.
- Timing is accurate to about 30 seconds.
- Notifications only work on macOS.

## Try it

```bash
git clone https://github.com/pawiromitchel/bcron.git
cd bcron
./build.sh
./bin/bcron daemon start
./bin/bcron
```
