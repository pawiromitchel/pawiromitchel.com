Developing automated cryptocurrency trading scripts requires addressing severe API constraints: strict request rate limits, millisecond-level timestamp drift penalties, and nonce collision under concurrent order dispatch.

While authoring the open-source [ftx-api-rest-extended](https://www.npmjs.com/package/ftx-api-rest-extended) client library, I engineered solutions for these exact challenges.

---

## 1. Concurrency and Nonce Synchronization

Exchange REST APIs validate that request nonces (typically millisecond timestamps) are strictly monotonically increasing. Under concurrent execution, two requests dispatched at the exact same millisecond fail with `Invalid Nonce`:

```text
Thread A: timestamp = 1700000000100 ──► [Exchange] OK
Thread B: timestamp = 1700000000100 ──► [Exchange] REJECT: Nonce not greater!
```

### The Monotonic Nonce Generator
To eliminate collisions without blocking worker threads:

```typescript
export class NonceManager {
  private lastNonce: number = 0;

  public getNextNonce(): number {
    const now = Date.now();
    if (now <= this.lastNonce) {
      this.lastNonce += 1;
    } else {
      this.lastNonce = now;
    }
    return this.lastNonce;
  }
}
```

## 2. Low-Latency HMAC SHA-256 Authentication

Request signatures must hash the method, endpoint path, nonce, and optional JSON body. Avoiding unnecessary string allocations minimizes V8 garbage collection pauses:

```typescript
import crypto from "crypto";

export interface RequestAuthHeaders {
  "FTX-KEY": string;
  "FTX-SIGN": string;
  "FTX-TS": string;
  "FTX-SUBACCOUNT"?: string;
}

export function signPayload(
  apiSecret: string,
  apiKey: string,
  method: string,
  path: string,
  nonce: number,
  body?: object,
  subaccount?: string
): RequestAuthHeaders {
  const bodyString = body ? JSON.stringify(body) : "";
  const payload = `${nonce}${method.toUpperCase()}${path}${bodyString}`;

  const signature = crypto
    .createHmac("sha256", apiSecret)
    .update(payload)
    .digest("hex");

  const headers: RequestAuthHeaders = {
    "FTX-KEY": apiKey,
    "FTX-SIGN": signature,
    "FTX-TS": nonce.toString(),
  };

  if (subaccount) {
    headers["FTX-SUBACCOUNT"] = encodeURIComponent(subaccount);
  }

  return headers;
}
```

## 3. Order Execution Pipeline: REST vs WebSocket

When executing market and limit orders, the decision between HTTP REST and full-duplex WebSockets depends on the pipeline phase:

```text
┌─────────────────────────────────────────────────────────────┐
│                 Algorithmic Trading Bot                     │
└──────────────┬───────────────────────────────▲──────────────┘
               │ Submit Order                  │ Execution Fill
               │ (Low-latency REST / WS)       │ (Stream via WS)
               ▼                               │
┌──────────────────────────────┐ ┌─────────────┴──────────────┐
│  Order Execution Gateway     │ │  Live Orderbook & Fills    │
│  (Strict Rate Limit Queue)   │ │  (Persistent WebSocket)    │
└──────────────────────────────┘ └────────────────────────────┘
```

| Channel | Recommended Use | Reason |
| :--- | :--- | :--- |
| **WebSocket Private Channel** | Order fills, balance updates | Zero-polling overhead; sub-5ms push notification. |
| **REST API Gateway** | Idempotent cancel, bulk orders | Predictable HTTP status codes and explicit retry semantics. |

## 4. Subaccount Risk Isolation

Never trade from primary exchange credentials. Segregating trading bots into dedicated subaccounts provides:
1. **Isolated Margin Pools**: A liquidated position cannot drain cold storage or hedge balances.
2. **Independent Rate Limits**: High-frequency order adjustments on one pair do not starve emergency cancellations on another.
