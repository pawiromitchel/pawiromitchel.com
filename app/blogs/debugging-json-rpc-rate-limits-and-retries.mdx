During high-volatility market events or popular mint drops, decentralized applications flood RPC providers with read requests. Without proper client-side resilient networking, users experience frozen balances, failed transaction submissions, and ubiquitous `429 Too Many Requests` errors.

Here is how to structure a production-grade Web3 RPC client with intelligent backoff, jitter, and request batching.

## 1. The Retry Problem: Why Naive Retries Cause Cascading Outages

When an RPC provider sheds load, naive immediate retries trigger a thundering herd effect:

```text
[Client 1] ─── Request 1 ───► [RPC Server] (Overloaded! Returns 429)
[Client 2] ─── Request 2 ───► [RPC Server] (Returns 429)
     │                               │
     ▼ (Immediate Retry)             ▼ (Immediate Retry)
[Client 1] ─── Request 1 ───► [RPC Server] (CPU 100% -> Crash)
[Client 2] ─── Request 2 ───► [RPC Server]
```

### Full Jitter Algorithm
To break client synchronization, implement **Exponential Backoff with Full Jitter**:

```text
Sleep = random(0, min(maxBackoff, base * 2^attempt))
```

```typescript
export interface RetryConfig {
  maxRetries: number;
  baseDelayMs: number;
  maxDelayMs: number;
}

export async function callRpcWithJitter<T>(
  fn: () => Promise<T>,
  config: RetryConfig = { maxRetries: 4, baseDelayMs: 200, maxDelayMs: 3000 }
): Promise<T> {
  let attempt = 0;

  while (true) {
    try {
      return await fn();
    } catch (error: any) {
      attempt++;
      
      const isRateLimited = error?.status === 429 || error?.code === -32005;
      const isNetworkError = error?.code === "ECONNRESET" || error?.code === "ETIMEDOUT";

      if (attempt > config.maxRetries || (!isRateLimited && !isNetworkError)) {
        throw error;
      }

      // Exponential cap
      const exponentialDelay = Math.min(
        config.maxDelayMs,
        config.baseDelayMs * Math.pow(2, attempt)
      );

      // Apply Full Jitter: random between 0 and exponentialDelay
      const jitteredSleep = Math.random() * exponentialDelay;

      await new Promise((resolve) => setTimeout(resolve, jitteredSleep));
    }
  }
}
```

## 2. Request Batching: Sizing and Boundaries

JSON-RPC allows array payloads to combine multiple method calls into a single HTTP round-trip:

```json
[
  {"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1},
  {"jsonrpc":"2.0","method":"eth_gasPrice","params":[],"id":2}
]
```

### The Pitfall
Sending batches of 100+ `eth_call`s causes node CPU spikes and proxy 504 timeouts.

**Recommended Production Limits**:
- **Max Batch Size**: 10–20 requests per array.
- **Compute Threshold**: Never mix heavyweight `eth_getLogs` with fast `eth_blockNumber` inside the same batch.

```typescript
export class RpcBatcher {
  private queue: Array<{ payload: any; resolve: Function; reject: Function }> = [];
  private timer: NodeJS.Timeout | null = null;

  constructor(private rpcUrl: string, private maxBatchSize = 15, private maxWaitMs = 15) {}

  public execute(method: string, params: any[] = []): Promise<any> {
    return new Promise((resolve, reject) => {
      this.queue.push({
        payload: { jsonrpc: "2.0", id: Date.now() + Math.random(), method, params },
        resolve,
        reject,
      });

      if (this.queue.length >= this.maxBatchSize) {
        this.flush();
      } else if (!this.timer) {
        this.timer = setTimeout(() => this.flush(), this.maxWaitMs);
      }
    });
  }

  private async flush() {
    if (this.timer) clearTimeout(this.timer);
    this.timer = null;

    const currentBatch = this.queue.splice(0, this.maxBatchSize);
    if (currentBatch.length === 0) return;

    try {
      const response = await fetch(this.rpcUrl, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(currentBatch.map((b) => b.payload)),
      });

      const results = await response.json();
      const resultMap = new Map(results.map((r: any) => [r.id, r]));

      for (const item of currentBatch) {
        const res = resultMap.get(item.payload.id);
        if (res?.error) {
          item.reject(res.error);
        } else {
          item.resolve(res?.result);
        }
      }
    } catch (err) {
      currentBatch.forEach((b) => b.reject(err));
    }
  }
}
```

## Summary Checklist
1. **Always Jitter Retries**: Avoid fixed delays (`sleep(1000)`).
2. **Cap Batch Sizes**: 15 requests per batch keeps execution sub-50ms.
3. **Partition by Method**: Keep compute-heavy queries on separate worker pools.
